## 本页解释粒度

每个核心片段都按开发者调试源码时真正会问的问题解释：

- 这个阶段的名字是什么意思，避免只写“清洗”“拒绝”“兜底”这类没有定义的词。
- 这段读取了哪些入参、class 字段、Map、数组、全局对象或 helper 返回值。
- 这段会不会修改 `queue/keys/bytes/dropped`，如果不修改也明确说出来。
- 数据从什么形状变成什么形状，例如原始错误事件变成脱敏、截断后的事件。
- 返回值代表什么业务语义，例如 `false` 是“没有入队”，不是网络失败。
- 空值、重复、超限、取消发送、能力不存在这些边界分支具体怎么走。

## EarlyErrorQueue：依赖

源码位置：`packages/element-utils/src/earlyErrorQueue/index.ts`

```ts
import estimateBytes from '../estimateBytes'
import enrichEarlyErrors from './browser/enrichEarlyErrors'
import getErrorKey from './core/getErrorKey'
import sanitizeEvent from './core/sanitizeEvent'
import sendEarlyErrorPayload from './transport/sendEarlyErrorPayload'
import takeGlobalEarlyErrors from './browser/takeGlobalEarlyErrors'
```

`EarlyErrorQueue` 是队列实例状态的唯一容器。这里的“实例状态”指会随着一次队列实例生命周期变化的字段，例如数组、去重索引、字节数和丢弃计数。

这些 import 分成三类：

- 纯逻辑 helper：`sanitizeEvent`、`getErrorKey`。它们只根据入参返回结果，不读写 class 字段，也不触碰浏览器全局。
- 实例状态 helper：`estimateBytes(this.queue)`。它不自己保存状态，只返回字节估算结果，由 class 写入 `this.bytes`。
- effect 边界：`takeGlobalEarlyErrors` 会读 `window.__EARLY_ERROR_QUEUE__`，`sendEarlyErrorPayload` 会发网络请求，`enrichEarlyErrors` 会读当前路由和时间；这些不放在 `core/**`。

这段 import 本身不产生副作用。真正读写状态发生在后面的 class 方法里。

## EarlyErrorQueue：内部配置类型

源码位置：`packages/element-utils/src/earlyErrorQueue/index.ts`

```ts
type EarlyErrorQueueRuntimeOptions = {
  maxCount: number
  maxBytes: number
  maxAge: number
  maxStackLength: number
  maxMessageLength: number
  maxHtmlLength: number
  sensitiveKeys: RegExp
  beforeEnqueue: EarlyErrorQueueOptions['beforeEnqueue']
}
```

这个类型只服务 class 内部，所以留在 `index.ts` 就近定义。

- `EarlyErrorQueueOptions` 是调用方传入的公共配置，允许字段缺省。
- `EarlyErrorQueueRuntimeOptions` 是 constructor 合并默认值后的内部配置，除 `beforeEnqueue` 以外都变成必填。
- 它不会被 export，因为业务代码不应该依赖“内部已经补齐默认值”的结构。

后续 `push`、`trimQueue`、`sanitizeEvent` 都读取 `this.options`；没有任何方法会重新写它，所以一个队列实例的容量和清洗规则在生命周期内固定。

## EarlyErrorQueue：实例字段

源码位置：`packages/element-utils/src/earlyErrorQueue/index.ts`

```ts
export default class EarlyErrorQueue {
  private readonly options: EarlyErrorQueueRuntimeOptions
  private readonly installedAt = Date.now()
  private readonly queue: EarlyErrorEvent[] = []
  private readonly keys = new Map<string, EarlyErrorEvent>()
  private bytes = 0
  private dropped = 0
```

这六个字段构成队列实例的全部状态，其中 `queue/keys/bytes/dropped` 会随调用变化：

- `options`：实例固定配置。constructor 写一次，后续只读。
- `installedAt`：实例创建时间。`push` 用它计算“队列已经活了多久”。
- `queue`：按入队顺序保存去重后的代表事件。新事件从尾部进入，容量裁剪从头部移除旧事件。
- `keys`：去重索引。key 来自 `getErrorKey`，value 指向 `queue` 里的同一个事件对象；这让重复事件可以直接更新已有对象。
- `bytes`：当前队列的估算字节数。只通过 `recalculateBytes` 或清空逻辑更新，不在多个分支里手动加减。
- `dropped`：因容量裁剪丢弃的旧事件数。它不统计 `maxAge` 超时拒绝，也不统计 `beforeEnqueue` 返回 `false`。

核心不变量是：只要事件还在 `queue` 里，`keys` 也必须能用同一个 key 找到它；事件被裁剪、take 或 clear 时，这两个结构要一起更新。

```ts
constructor(options: EarlyErrorQueueOptions = {}) {
  this.options = {

    maxBytes: options.maxBytes ?? DEFAULT_EARLY_ERROR_MAX_BYTES,

      options.maxStackLength ?? DEFAULT_EARLY_ERROR_MAX_STACK_LENGTH,

      options.maxMessageLength ?? DEFAULT_EARLY_ERROR_MAX_MESSAGE_LENGTH,
    maxHtmlLength:
      options.maxHtmlLength ?? DEFAULT_EARLY_ERROR_MAX_HTML_LENGTH,
    sensitiveKeys:
      options.sensitiveKeys ?? DEFAULT_EARLY_ERROR_SENSITIVE_KEYS,
    beforeEnqueue: options.beforeEnqueue,
  }
}
```

constructor 做两件事：

- 读取调用方传入的 `options`。
- 对每个可选字段执行 `options.foo ?? DEFAULT_FOO`，把它补成 class 内部稳定使用的 `this.options`。

这里没有拆 `createFullOptions`。原因是每一项都是线性默认值合并，没有校验、派生字段或跨模块复用；拆 helper 会让读者多跳一层，却不会让主流程更清楚。

这个阶段只写 `this.options`。它不会写 `queue/keys/bytes/dropped`，所以创建实例时队列仍然是空的。

## EarlyErrorQueue：字节重算

源码位置：`packages/element-utils/src/earlyErrorQueue/index.ts`

```ts
private recalculateBytes = (): void => {
  this.bytes = estimateBytes(this.queue)
}
```

这段只写 `this.bytes`，不修改 `queue/keys/dropped`。

这里选择“整体重算”，不是“每次入队加上新事件字节数”，原因是队列里的事件对象可能原地变化。例如重复错误命中后会直接改已有事件的 `count` 和 `lastSeen`；容量裁剪也可能一次删除多条旧事件。整体重算虽然要遍历队列，但队列有 `maxCount` 上限，复杂度可控，状态也更不容易算错。

## EarlyErrorQueue：移除最旧事件

源码位置：`packages/element-utils/src/earlyErrorQueue/index.ts`

```ts
private removeFirst = (): void => {
  const removed = this.queue.shift()
  if (!removed) return

  this.keys.delete(getErrorKey(removed))
  this.dropped += 1
  this.recalculateBytes()
}
```

`removeFirst` 的语义是“容量裁剪时丢弃最旧事件”。它不是业务过滤，也不是读取队列。

执行顺序是：

1. `this.queue.shift()` 取出最旧事件；队列为空时提前返回，没有状态变化。
2. 用同一个事件重新算 key，并从 `this.keys` 删除对应索引，保证 `queue` 和 `keys` 同步。
3. `this.dropped += 1`，这是唯一增加 `dropped` 的地方。
4. 重算 `bytes`，让统计和后续容量判断使用最新队列内容。

返回值是 `void`。调用方不靠返回值判断是否删除成功，而是依赖 `queue/keys/bytes/dropped` 四个状态被同步更新。

## EarlyErrorQueue：容量裁剪

源码位置：`packages/element-utils/src/earlyErrorQueue/index.ts`

```ts
private trimQueue = (): void => {
  this.recalculateBytes()

  while (
    this.queue.length > this.options.maxCount ||
    this.bytes > this.options.maxBytes
  ) {
    this.removeFirst()
  }
}
```

`trimQueue` 的语义是“把队列裁剪回配置允许的大小”。它只在新事件入队后调用。

执行顺序是：

1. 先调用 `recalculateBytes()`，让 `this.bytes` 反映当前完整队列。
2. 只要条数超过 `maxCount`，或者字节数超过 `maxBytes`，就调用 `removeFirst()` 删除队头旧事件。
3. `removeFirst()` 每删一次都会同步更新 `keys/dropped/bytes`。

最终要保证两个不变量同时成立：

- `this.queue.length <= this.options.maxCount`
- `this.bytes <= this.options.maxBytes`

边界情况：如果刚入队的新事件本身就超过 `maxBytes`，队列可能把它也裁掉；当前 `push` 仍会返回 `true`，表示事件通过了入队流程，但最后没有被缓存下来。`dropped` 会记录这次容量裁剪。

## EarlyErrorQueue：统计快照

源码位置：`packages/element-utils/src/earlyErrorQueue/index.ts`

```ts
private getStats = (): EarlyErrorQueueStats => ({
  count: this.queue.length,
  bytes: this.bytes,
  dropped: this.dropped,
})
```

`getStats` 是 class 私有方法，不作为 public API 暴露。它读取的是当前内存状态：

- `count`：当前 `queue.length`，也就是还没被消费的代表事件数量。
- `bytes`：最近一次重算后的估算字节数。
- `dropped`：实例生命周期内因容量裁剪丢弃的旧事件数量。

它不修改任何状态。`createPayload` 会在调用 `take()` 之前先读它，所以 payload 里的 stats 描述的是“消费前的队列状态”，不是清空后的状态。

## EarlyErrorQueue：push 的入队前过滤与字段清洗

源码位置：`packages/element-utils/src/earlyErrorQueue/index.ts`

```ts
push = (event: EarlyErrorEvent): boolean => {
  if (Date.now() - this.installedAt > this.options.maxAge) return false

  const sanitizedEvent = sanitizeEvent(event, this.options)
  const filteredEvent = this.options.beforeEnqueue
    ? this.options.beforeEnqueue(sanitizedEvent)
    : sanitizedEvent

  if (!filteredEvent) return false
```

这段发生在真正写入 `queue` 之前，所以叫“入队前过滤与字段清洗”。

术语先定义清楚：

- “过滤”指决定这个事件是否允许继续进入队列流程。
- “字段清洗”指对事件字段做脱敏、截断和兜底，例如 URL query 里的 token 被替换，`message/stack/outerHTML` 被限制长度。
- “拒绝入队”指返回 `false`，并且不写 `queue/keys/bytes/dropped`。

执行顺序是：

1. `Date.now() - this.installedAt > this.options.maxAge`：判断队列是否已经超过早期捕获窗口。超时直接 `return false`，不会调用 `sanitizeEvent`，也不会触发业务回调。
2. `sanitizeEvent(event, this.options)`：把原始事件转换成清洗后的事件。这个函数返回新对象，不写 class 状态。
3. `beforeEnqueue`：业务侧最后一次过滤或改写机会。它接收的是已经清洗过的事件，不会拿到未脱敏 URL。
4. `if (!filteredEvent) return false`：业务返回 `false` 时丢弃事件。这个丢弃不是容量裁剪，所以 `dropped` 不增加。

能走到下一段代码时，`filteredEvent` 一定是准备进入去重流程的事件。

## EarlyErrorQueue：push 的重复错误合并分支

源码位置：`packages/element-utils/src/earlyErrorQueue/index.ts`

```ts
const key = getErrorKey(filteredEvent)
const existingEvent = this.keys.get(key)

if (existingEvent) {
  existingEvent.count += 1
  existingEvent.lastSeen = filteredEvent.timestamp
  this.recalculateBytes()
  return true
}
```

“重复错误”不是指两个对象完全相等，而是 `getErrorKey(filteredEvent)` 生成的 key 已经存在于 `this.keys`。

这段读取两个值：

- `filteredEvent`：已经通过字段清洗和业务过滤的事件。
- `this.keys`：当前队列的去重索引。

命中 `existingEvent` 时，代码不会向 `queue` 追加新项，只会原地更新已有代表事件：

- `count += 1` 记录重复出现次数。
- `lastSeen = filteredEvent.timestamp` 记录最近一次出现时间。
- 重算 `bytes`，因为已有事件内容变了。
- 返回 `true` 表示这次事件被队列接受并合并。

这个分支不会修改 `keys` 的条目数量，也不会修改 `dropped`。`queue.length` 保持不变。

## EarlyErrorQueue：push 的新事件入队和容量裁剪

源码位置：`packages/element-utils/src/earlyErrorQueue/index.ts`

```ts
  this.queue.push(filteredEvent)
  this.keys.set(key, filteredEvent)
  this.trimQueue()
  return true
}
```

未命中去重索引时，说明这个错误是当前队列里新的代表事件。

- `this.queue.push(filteredEvent)` 把事件放到队尾。
- `this.keys.set(key, filteredEvent)` 建立去重索引，value 和队列项是同一个对象。
- `this.trimQueue()` 负责容量限制，可能把队头旧事件移除。
- 返回 `true` 表示新事件已入队。

这里会写 `queue`、`keys`，并且可能通过 `trimQueue()` 间接写 `bytes/dropped`。如果队列超出 `maxCount` 或 `maxBytes`，`trimQueue()` 会从最旧事件开始删，直到容量回到限制内。

返回 `true` 的含义是“事件通过了入队流程”。它不保证事件最终一定还留在队列里，因为极端情况下新事件本身超过 `maxBytes`，会被刚调用的 `trimQueue()` 裁掉。

## EarlyErrorQueue：接管 bootstrap 全局队列

源码位置：`packages/element-utils/src/earlyErrorQueue/index.ts`

```ts
captureGlobal = (): number => {
  const events = takeGlobalEarlyErrors()
  events.forEach((event) => this.push(event))
  return events.length
}
```

这里的“接管”指完整 SDK 初始化完成后，把 inline bootstrap 在 `window.__EARLY_ERROR_QUEUE__` 暂存的事件转移到当前 `EarlyErrorQueue` 实例中。

执行流程是：

1. `takeGlobalEarlyErrors()` 从 `window.__EARLY_ERROR_QUEUE__` 取出并清空 inline 队列。
2. `events.forEach((event) => this.push(event))` 把每个事件重新走当前实例的入队流程，所以仍然会执行字段清洗、业务过滤、去重和容量裁剪。
3. 返回 `events.length`，它表示“从全局队列读到了多少条原始事件”，不是最终成功留在当前队列里的数量。

边界行为：如果 `beforeEnqueue` 丢弃部分事件，或者容量裁剪删掉旧事件，`captureGlobal()` 的返回值不会反映这些变化。要看当前队列内容，应调用 `peek()`。

## EarlyErrorQueue：take/peek 的消费式读取和只读快照

源码位置：`packages/element-utils/src/earlyErrorQueue/index.ts`

```ts
take = (): EarlyErrorEvent[] => {
  const events = this.queue.slice()
  this.queue.length = 0
  this.keys.clear()
  this.bytes = 0
  return events
}

peek = (): EarlyErrorEvent[] => this.queue.slice()
```

`take` 和 `peek` 都返回数组浅拷贝，但语义完全不同：

- `take` 是“消费式读取”。它先 `slice` 出当前事件快照，再清空 `queue`、`keys` 和 `bytes`。用于上报前取走事件，避免同一批错误重复发送。
- `peek` 是“只读快照”。它只返回 `queue.slice()`，不会清空队列，也不会修改 `keys/bytes/dropped`。

两者返回的都是浅拷贝；数组是新的，但里面的事件对象不是深拷贝。调用方不应该修改返回事件对象后再假设队列内部完全不受影响。

## EarlyErrorQueue：主动清空

源码位置：`packages/element-utils/src/earlyErrorQueue/index.ts`

```ts
clear = (): void => {
  this.queue.length = 0
  this.keys.clear()
  this.bytes = 0
}
```

`clear` 的语义是“主动放弃当前缓存”。它写三个状态：

- `queue.length = 0`：丢弃当前所有事件。
- `keys.clear()`：清空去重索引，避免旧 key 影响后续事件。
- `bytes = 0`：当前队列已经为空，字节估算同步归零。

它不会重置 `dropped`。`dropped` 描述的是这个实例生命周期内发生过多少次容量裁剪；清空当前队列不等于清空生命周期统计。

## EarlyErrorQueue：createPayload 的消费队列和补上下文

源码位置：`packages/element-utils/src/earlyErrorQueue/index.ts`

```ts
  createPayload = (
    options: Omit<
      FlushEarlyErrorsOptions,
      'url' | 'transport' | 'credentials'
    > = {}
  ): EarlyErrorPayload => {
    const reason = options.reason ?? EARLY_ERROR_FLUSH_REASON.INIT
    const context = options.context ?? {}
    const stats = this.getStats()
    const events = enrichEarlyErrors(this.take(), context, reason)
```

`createPayload` 把“内存队列里的事实事件”转换成“可以发送给监控后端的 payload”。它会消费队列。

这里的顺序很重要：

- 先读 `stats`，此时队列还没被 `take()` 清空，所以 `count/bytes/dropped` 是消费前状态。
- 再调用 `this.take()`，读取并清空当前队列。
- `enrichEarlyErrors` 给每个事件补 `context`、`flushReason`、`flushedAt` 和 `source`。

返回值里的 `events` 是补齐上下文后的事件数组；`context` 是这次 flush 的上下文原值；`stats` 是消费前队列统计。

边界行为：调用 `createPayload` 本身就会消费队列，即使后续没有发送。只想预览时要用 `peek()`，不要调用 `createPayload()`。

## EarlyErrorQueue：flush 的发送前处理和取消发送

源码位置：`packages/element-utils/src/earlyErrorQueue/index.ts`

```ts
  flush = async (options: FlushEarlyErrorsOptions) => {
    const payload = this.createPayload(options)
    const processedPayload = options.beforeSend
      ? options.beforeSend(payload)
      : payload

    if (!processedPayload) {
      return {
        success: false,
        transport: options.transport ?? EARLY_ERROR_TRANSPORT.FETCH,
        count: 0,
        bytes: 0,
      }
    }
```

`flush` 是完整发送入口。它先调用 `createPayload(options)`，所以第一步已经消费并清空队列；然后才执行发送前回调 `beforeSend`。

`beforeSend` 的语义是“发送前最后一次改写或取消 payload”：

- 没传 `beforeSend`：直接发送原 payload。
- 返回新的 payload：发送返回值。
- 返回 `false`：取消发送。

因此 `beforeSend` 返回 `false` 时不会发请求，但队列已经在 `createPayload` 阶段被清空，当前实现不会自动把事件放回队列。

这个返回对象表示“本次发送被取消”，不是网络失败：

- `success: false`
- `count: 0`
- `bytes: 0`
- `transport` 使用调用方传入值，没有传则按 `FETCH`

```ts
const isErrorEvent = (event: ErrorEvent | Event): event is ErrorEvent => {
  return (
    isBrowser() &&
    typeof ErrorEvent !== 'undefined' &&
    event instanceof ErrorEvent
  )
}
```

这三个判断服务于同一个问题：浏览器的 `error` 事件既可能表示 JS 运行时异常，也可能表示资源加载失败。

- `isResourceTarget`：判断 `event.target` 是否像资源元素。这里只看有没有 `tagName`，因为资源错误通常来自 `<script>`、`<img>`、`<link>` 等元素。
- `isWindowTarget`：排除 window 自身。它先走 `isBrowser()`，避免非浏览器环境直接读取 `window`。
- `isErrorEvent`：判断事件是不是 JS 运行时错误。它先确认 `ErrorEvent` 构造器存在，再执行 `instanceof`，兼容没有该构造器的环境。

这些 helper 只做类型收窄，不创建事件，也不写队列状态。

源码位置：`packages/element-utils/src/earlyErrorQueue/browser/createEvents.ts`

```ts
export const createErrorEvent = (
  event: ErrorEvent | Event
): EarlyJSErrorEvent | EarlyResourceErrorEvent | null => {
  const target = event.target

  if (isResourceTarget(target) && !isWindowTarget(target)) {
    const tagName = target.tagName
    const resourceUrl = target.src ?? target.href

    return {
      ...createBaseEvent(),
      type: EARLY_ERROR_TYPE.RESOURCE,
      message: `Failed to load ${String(tagName ?? 'resource').toLowerCase()}: ${resourceUrl ?? ''}`,
      tagName,
      resourceUrl,
      outerHTML: target.outerHTML,
    }
  }
```

这里先走资源错误分支，因为资源加载失败也会触发 `error` 事件，但它不是 JS `ErrorEvent` 的业务语义。

命中资源分支时，事件会带上：

- `tagName`：失败元素类型。
- `resourceUrl`：`src` 或 `href`。
- `outerHTML`：失败元素快照，后续入队前会被 `sanitizeEvent` 截断。

返回值是 `EarlyResourceErrorEvent`。如果 `target` 不像资源元素，代码继续往 JS 错误分支走。

## enrichEarlyErrors：flush 时补齐业务上下文和发送元信息

源码位置：`packages/element-utils/src/earlyErrorQueue/browser/enrichEarlyErrors.ts`

```ts
const enrichEarlyErrors = (
  events: EarlyErrorEvent[],
  context: EarlyErrorContext = {},
  reason: EARLY_ERROR_FLUSH_REASON = EARLY_ERROR_FLUSH_REASON.INIT
): EnrichedEarlyErrorEvent[] => {
  const flushedAt = Date.now()
  const route = isBrowser() ? window.location.pathname : undefined

  return events.map((event) => ({
    ...event,
    ...context,
    route: context.route ?? route,
    userId: context.userId ?? 'anonymous',
    flushedAt,
    flushReason: reason,
    source: 'early_error_queue',
  }))
}
```

这段把“早期捕获时还不知道的信息”补回事件。早期错误发生时，完整 SDK 可能还没初始化，所以当时拿不到 appId、release、userId、sessionId 等业务上下文。

数据合并顺序是：

1. `...event`：保留原始早期错误字段。
2. `...context`：把 SDK 初始化后拿到的业务上下文合并进去，同名字段由 context 覆盖。
3. `route: context.route ?? route`：调用方传了 route 就用调用方的；没传且在浏览器环境中，就用当前 `window.location.pathname`。
4. `userId: context.userId ?? 'anonymous'`：没有用户信息时给后端稳定默认值。
5. `flushedAt/flushReason/source`：标记这批事件何时、为什么、从哪个模块被发送。

返回的是新数组，原 `events` 数组不会被清空；清空发生在 `EarlyErrorQueue.createPayload` 调用 `take()` 时。

## script.tsx：push 的早期窗口过滤和原地字段清洗

源码位置：`packages/element-utils/src/earlyErrorQueue/script.tsx`

```ts
  function push(event) {
    try {
      if (now() - installedAt > MAX_AGE) return

      event.message = safeString(event.message).slice(0, MAX_MESSAGE)
      event.pageUrl = sanitizeUrl(event.pageUrl || location.href)
      event.filename = sanitizeUrl(event.filename)
      event.resourceUrl = sanitizeUrl(event.resourceUrl)
      event.reportUrl = sanitizeUrl(event.reportUrl)
      event.stack = event.stack
        ? String(event.stack).slice(0, MAX_STACK)
        : undefined
      event.outerHTML = event.outerHTML
        ? String(event.outerHTML).slice(0, MAX_HTML)
        : undefined
```

inline 版本的 `push` 和 TS class 的 `push` 语义相近，但实现更克制，因为它要复制到业务页面里：

- `now() - installedAt > MAX_AGE`：超过早期窗口直接返回，不再捕获后续事件。
- `event.message/pageUrl/filename/resourceUrl/reportUrl/stack/outerHTML`：直接在原对象上改写，完成截断和 URL 脱敏。
- `try/catch` 包住整个入队流程：任何清洗或入队异常都会被吞掉，避免早期错误捕获脚本本身影响页面。

这里的“清洗”同样指字段处理：消息截断、URL query 脱敏、堆栈和 HTML 快照限制长度。和 TS 模块不同，inline 版本为了减少代码体积直接修改传入的 `event` 对象。

## script.tsx：去重合并、首次入队和容量裁剪

源码位置：`packages/element-utils/src/earlyErrorQueue/script.tsx`

```ts

      var existing = keys[key]

      if (existing) {
        existing.count += 1
        existing.lastSeen = event.timestamp || now()
        recalculateBytes()
        return
      }

      keys[key] = event
```

inline 版本的状态变化和 TS 队列一致：

- `getKey(event)`：把事件转换成去重 key。

## script.tsx：take/peek/stop/getStats 全局接管协议

源码位置：`packages/element-utils/src/earlyErrorQueue/script.tsx`

```ts
    take: function () {
      var copy = queue.slice()
      queue.length = 0
      keys = {}
      bytes = 0
      return copy
    },
    peek: function () {
      return queue.slice()
    },
    stop: stop,
    getStats: function () {
      return {
        count: queue.length,
        bytes: bytes,
        dropped: dropped,
      }
    },
  }

  window.addEventListener('error', onError, true)
  window.addEventListener('unhandledrejection', onUnhandledRejection)
  installReportingObserver()
})()
```

全局协议和 TS 接管函数配合：

- `take`：被 `takeGlobalEarlyErrors` 调用。它返回 `queue.slice()` 的副本，然后清空 `queue/keys/bytes`，语义是“交出早期缓存”。
- `peek`：只返回副本，不清空，适合调试。
- `stop`：移除 `error/unhandledrejection` 监听，并断开 `ReportingObserver`，语义是“完整 SDK 已接管，bootstrap 停止继续收集”。
- `getStats`：返回当前 `count/bytes/dropped`，用于调试或接管前观测。

最后三行是真正安装监听的地方。`error` 使用 capture 阶段，是为了捕获资源加载失败这类不会冒泡到 window bubble 阶段的事件。

这两个类型描述的是 TS 模块和 copy-only script 之间的边界：

- `push` 接收 `Partial<EarlyErrorEvent>`，因为 inline 阶段可能只能拿到部分字段。

## 关键不变量

- `queue` 和 `keys` 必须同步：新增事件时一起写，裁剪或清空时一起删。
- `bytes` 只通过 `recalculateBytes` 或清空逻辑更新，避免多个分支各自手动维护。
- `dropped` 只统计容量裁剪导致的旧事件丢弃，不统计业务过滤或超时拒绝。
- `createPayload` 和 `flush` 都会消费队列；调用前如果只是查看，应使用 `peek`。
- `script.tsx` 是复制使用的 inline script，不能因为 TS 模块已经有工具函数就引入 import。
